# Audit de l'app Bovo — 9 juin 2026

Périmètre : `app/` (Astro 4 statique + Capacitor 8, Supabase, Kkiapay, PWA), branche `feat/capacitor-mobile`.
Méthode : 5 audits parallèles (sécurité, qualité de code, tests, mobile, performance/PWA), puis vérification adversariale des 10 constats les plus lourds — **les 10 ont été confirmés sur le code réel**.

⚠️ État de mise en production : **l'app n'encaisse aucun paiement réel, perd des réservations hors-ligne, expose une faille XSS exploitable côté admin, et ses builds mobiles sont actuellement cassés.** À ne pas mettre en prod en l'état.

---

## 🔴 Bloquants (à corriger avant toute mise en prod)

### B1 — Kkiapay figé en mode sandbox : zéro encaissement réel, mais marqué « payé » en base
`src/pages/chef/recap.astro:171-182`, `src/pages/demenagement/recap.astro:194-211`
Les deux pages appellent `window.openKkiapayWidget({ ..., sandbox: true })` en dur, et le fallback de clé est `'DEMO'` (la variable `PUBLIC_KKIAPAY_PUBLIC_KEY` est vide dans `.env`). En production : aucun argent débité, mais le callback `success` écrit quand même `deposit_status='paid'` + un `transactionId` sandbox en base. Le helper correct `src/lib/kkiapay.ts` (`openDeposit`, qui calcule `sandbox = !import.meta.env.PROD`) existe mais **n'est importé nulle part**.
→ Router les deux recaps via `openDeposit()`, renseigner la vraie clé publique, échouer explicitement si la clé manque (pas de `?? 'DEMO'`).

### B2 — Aucune vérification serveur du paiement → acompte forgeable
`src/pages/chef/recap.astro:122-142`, `src/pages/demenagement/recap.astro:145-166`
Le statut `paid` et le `transactionId` proviennent du navigateur. Pas de webhook, pas d'appel serveur à l'API Kkiapay avec la clé privée pour confirmer la transaction et le montant. Le montant de l'acompte (20 %) est lui-même calculé côté client à partir du `sessionStorage` manipulable.
→ Vérifier le paiement via une Edge Function (`api.kkiapay.me/.../transactions/status` + clé privée), recalculer le montant attendu côté serveur, n'autoriser `paid` que via `service_role`.

### B3 — Politique RLS d'insertion totalement ouverte
`supabase/schema.sql:239` — `create policy "users insert reservations" ... with check (true)`
N'importe quel visiteur anonyme peut insérer une réservation avec **n'importe quelles valeurs** : `deposit_status='paid'`, `user_id` d'autrui, `estimated_total_xof` arbitraire, `status` arbitraire. Aucun trigger, aucun grant colonne, aucune contrainte ne l'empêche (vérifié sur tout `supabase/`). C'est le levier technique de B2 et de B4.
→ Restreindre le `with check` : forcer `user_id IS NULL` (invité) ou `user_id = auth.uid()` (connecté), `deposit_status='none'`, `status='pending'`, `assigned_worker_id IS NULL`. Réserver les colonnes sensibles au `service_role`/admin.

### B4 — XSS stocké exécutable dans la session admin
`src/pages/admin/reservations.astro:115-153, 184-224`
`guest_name`, `guest_email` et le `payload` JSON sont injectés via `innerHTML` sans échappement (le `JSON.stringify` n'échappe pas `<` `>` `/`). Combiné à B3, un attaquant anonyme soumet une réservation avec `guest_name = "<img src=x onerror=...>"` ; le script s'exécute dans le navigateur de l'admin connecté. À noter : la page voisine `admin/index.astro:715` possède une fonction `escapeHtml` — c'est une omission propre à `reservations.astro`.
→ Échapper toute donnée utilisateur/DB (fonction `escapeHtml` partagée ou `textContent`).

### B5 — Réservation perdue silencieusement si la soumission a lieu hors-ligne
`src/pages/menage/recap.astro:148-175` (même schéma dans les 5 recaps)
Au clic « Envoyer » : l'échec d'insert Supabase est seulement `console.warn` (la variable `saved` est calculée puis jamais relue), puis `clearState()` efface le `sessionStorage` **avant** toute confirmation de succès, puis la redirection `wa.me` échoue hors-ligne (cross-origin, hors service worker). Bilan : 7 étapes de saisie perdues, rien en base, aucun message. C'est le pire échec produit possible sur réseau intermittent (cas nominal au Bénin).
→ Ne `clearState` qu'après succès confirmé ; tester `navigator.onLine` + bouton « Réessayer » ; idéalement file d'attente locale rejouée sur l'événement `online`.

### B6 — Builds natifs Android & iOS actuellement cassés
`android/capacitor.settings.gradle:11-12`, `android/app/capacitor.build.gradle:14`, `ios/App/CapApp-SPM/Package.swift:17,29`
Les projets natifs référencent encore `@capacitor/push-notifications`, supprimé de `node_modules` (le projet utilise désormais `@capacitor-firebase/messaging`). `npx cap sync` n'a jamais été relancé après le changement : Gradle et Xcode échouent sur un chemin de package inexistant, et aucun des deux plugins Firebase n'est embarqué côté natif.
→ `npx cap sync` (android + ios), vérifier que les fichiers listent bien `@capacitor-firebase/*`, rebuilder.

## 🟠 Élevés

### E1 — `user_id` jamais rattaché aux réservations → espace client toujours vide
Les 5 recaps insèrent en mode invité (`guest_*`) sans lire la session Supabase. Or `compte/reservations.astro:206-210` filtre `.eq('user_id', user.id)` et la RLS exige `auth.uid() = user_id`. Un client connecté qui réserve ne verra jamais sa réservation, ne pourra pas la re-réserver en 1 clic, ni laisser d'avis (la policy `reviews` exige aussi `user_id = auth.uid()`).
→ Lire `supa.auth.getSession()` dans chaque recap, ajouter `user_id: session?.user.id ?? null` au payload.

### E2 — PWA non installable : toutes les icônes du manifest sont en 404
`public/manifest.webmanifest:18-61` — les 7 entrées `icons` pointent vers des `.webp` (`../icons/icon-*.webp`) qui n'existent pas dans `dist/icons/` (seulement des PNG). Les `.webp` sont à la racine `app/icons/`, jamais copiée dans `dist/` par Astro. Le critère Chrome (icônes 192+512 valides) n'est pas rempli → aucun prompt d'installation, pour une app dont la distribution repose sur le PWA.
→ Pointer vers `/icons/icon-192.png` et `/icons/icon-512.png` (`purpose:"any"`) + entrées séparées maskable.

### E3 — UPDATE `reservations` sans `WITH CHECK`
`supabase/schema.sql:240` — le propriétaire peut modifier tous les champs de sa résa (`status='done'`, `deposit_status='paid'`, `estimated_total_xof`, réaffecter `user_id`).
→ Ajouter un `with check` interdisant la modification des colonnes sensibles, ou limiter l'UPDATE client à `cancelled`.

### E4 — 54 Ko de bundle Supabase chargés pour rien sur la page d'accueil
`src/pages/index.astro:220-223` — `if (false && supa)` (code mort) mais `getSupabase()` est appelé : Rollup conserve l'instanciation du client → `dist/_astro/supabase.*.js` (208 Ko brut / 54 Ko gzip) payé par chaque visiteur de la landing pour rien.
→ Supprimer l'import mort de la home ; sur les recaps, passer à un `import()` dynamique au clic « Envoyer ».

### E5 — Fonts & libs tierces synchrones, non cachées offline
Google Fonts (2 familles × 8 graisses, ~120-180 Ko cross-origin, `Layout.astro:94-99`), Leaflet via unpkg synchrone bloquant sur 6 pages (`MapPicker.astro:20`), Kkiapay `cdn.kkiapay.me/k.js` synchrone. Tous ignorés par le service worker (cross-origin) → premier poste de poids, lent sur 3G.
→ Auto-héberger 3-4 graisses subset (woff2) + précache SW ; installer Leaflet en npm + lazy-load ; charger Kkiapay au clic.

### E6 — Aucun signing release Android ; distribution d'un APK debug
`android/app/build.gradle:19-26` — bloc `release` sans `signingConfig`, aucun keystore. Le seul artefact (`~/Desktop/bovo-debug.apk`, 7 juin) est signé debug : non publiable, sans protections release.
→ Créer un keystore d'upload (via `keystore.properties` gitignoré), ajouter `signingConfigs.release`, viser un `.aab` + Play App Signing.

### E7 — Config Firebase absente + chaîne push iOS incomplète
Pas de `google-services.json` (Android) ni `GoogleService-Info.plist` (iOS). Côté iOS, ni entitlement `aps-environment`, ni `UIBackgroundModes: remote-notification`, ni forwarding APNs dans `AppDelegate.swift` (omis par `PUSH_SETUP.md`). Le push est donc inopérant de bout en bout.
→ Suivre `PUSH_SETUP.md` §2-4, compléter `AppDelegate` (forwarding APNs) et le doc.

### E8 — Tout le travail mobile est non commité
`android/`, `ios/`, `capacitor.config.ts`, `src/lib/native.ts`, `src/lib/push.ts`, `supabase/functions/send-push/`, la migration `device_tokens` : tous en `??` dans `git status` (malgré `PUSH_SETUP.md` qui affirme « déjà dans le repo »). Risque de perte totale ; le CI ne voit rien.
→ Nettoyer les fichiers dupliqués ` 2.*` (cf. M-mobile) puis commiter.

## 🟡 Moyens

- **Open redirect** via `next` — `compte/connexion.astro:59-60`, `auth/callback.astro:58-59` : `next.startsWith('/')` laisse passer `//evil.com`. → exiger `&& !next.startsWith('//')`.
- **Prix Airbnb qui gonfle** au retour sur la page options — `airbnb/options.astro:50,72,77` : `base = estimatedPerTurnover` (déjà = base+options) se recompose. Le montant *soumis* reste correct (recap recalcule depuis le catalogue), mais l'affichage est faux. → repartir du prix catalogue dans `compute()`.
- **Pas de garde d'étapes** : recap soumissible avec un état vide (deep-link, session expirée, nouvel onglet) → demande avec `guest_name: undefined`, `scheduled_at: null`. → rediriger vers l'étape 1 si champs obligatoires manquants.
- **`min` des champs date figé au build** (site statique) — `menage/creneau.astro:14`, etc. : sans rebuild régulier, réservation possible pour une date passée. → poser `min` côté client + revalider au clic.
- **Validation contact divergente** : ménage/plombier valident le téléphone (≥8 chiffres) et rendent l'email optionnel ; airbnb/chef/déménagement acceptent « a » comme téléphone et exigent l'email. → extraire `validPhone`/`validEmail` partagés.
- **`window.open` WhatsApp après `await`** bloqué par les anti-popups (flux « créer mon compte ») — naviguer dans l'onglet courant ou ouvrir avant l'await.
- **Échec Supabase silencieux + aucun timeout** : `await insert` peut pendre indéfiniment (« Envoi en cours… » bloqué). → `AbortSignal.timeout(~8s)` + message.
- **Tunnel plombier actif** alors que la migration n'est pas appliquée (CHECK rejette `'plombier'`) : toute résa plombier part sur WhatsApp uniquement, sans trace DB. → appliquer la migration ou rediriger `/plombier/`.
- **Échec paiement = `deposit_status:'none'`** indiscernable d'un « pas d'acompte voulu » — utiliser `'pending'` ou un statut dédié.
- **Restauration étape 1 Airbnb cassée** (`airbnb/index.astro:89` compare `"2"` à `data-value="2-3"`) — stocker l'id de l'option.
- **Sitemap expose les URLs `/admin/`** — `astro.config.mjs:7` (`sitemap()` sans filtre) liste 51 URLs noindex dont `/admin/reservations/`. → filtrer sur la seule home, ou retirer l'intégration.
- **Service worker** : assets non hashés jamais revalidés (cache-first + version manuelle `sw.js:5`), `RUNTIME_CACHE` non borné (gonfle à chaque déploiement). → stale-while-revalidate hors `/_astro/*`, purge à l'`activate`.
- **PII en sessionStorage** (nom, téléphone, email, géoloc) — exposition limitée mais aggrave l'impact d'un XSS.
- **Tables worker world-readable** (`schema.sql:244-246`, `using(true)`) : compétences/zones/plannings lisibles par tout visiteur. → restreindre à `authenticated`/admin.
- **`android:allowBackup="true"`** (`AndroidManifest.xml:4`) : données WebView (token push, session) sauvegardées/restaurables. → `false` ou règles d'exclusion.
- **Incohérence de versions** : package.json `0.1.0` vs Android/iOS `1.0`. **Fichiers dupliqués ` 2.*`** packagés dans l'app native. **`DEPLOYMENT.md` obsolète** (couvre seulement le web, étape « git init » fausse).

### Accessibilité
- État de sélection invisible aux lecteurs d'écran (aucun `aria-pressed`/`role="radio"` dans tout `src/`).
- Erreurs/hints/prix dynamiques non annoncés (aucun `aria-live`/`role="alert"`).
- Étapes de tunnel sans `<form>` → Entrée ne valide pas, `required` inopérant.
- Contraste WhatsApp illisible sur la page offline (≈1,9:1, échec AA). Cibles tactiles sous 44 px (boutons +/- durée).

## ✅ Points sains (vérifiés)
- Aucun secret en dur ; `.env` gitignoré ; clé Supabase exposée = clé anon/publishable (normal) ; pas de fichier Firebase commité.
- RLS activé sur toutes les tables ; policies `addresses`/`reviews`/`profiles`/`device_tokens` correctement cloisonnées par `auth.uid()` ; fonctions `SECURITY DEFINER` avec `search_path` fixé.
- Capacitor : pas de `server.url` distant, pas de cleartext HTTP, permissions Android minimales (`INTERNET`), ATS iOS strict, SDK à jour (minSdk 24 / target 36, iOS 15).
- Supabase non configuré → fallback WhatsApp propre. Reload mi-tunnel → state restauré. Pas d'image bitmap (SVG inline), HTML 2-5 Ko gzip.
- `matching.test.ts` et `state.test.ts` de bonne qualité ; les 2 derniers runs Playwright étaient verts (mais antérieurs au refactor du 6-7 juin).

## Tests — état
- **52 tests unitaires** (catalog, state, matching) + **17 e2e** (homepage, auth rendu seul, tunnel ménage complet, view-transitions).
- **Non exécutables sur cette machine** (aucun runtime Node installé) — impossible de confirmer pass/fail.
- Trous critiques : **calcul de prix non testé** (formules inline dans les `.astro`), **paiement Kkiapay zéro test** (+ risque de listeners empilés → double soumission), **3 tunnels sur 4 sans e2e complet** (déménagement, qui porte le paiement, n'en a aucun), **soumission de réservation jamais exercée**, **auth exclue de tout test réel**.
- Le e2e ménage contourne un vrai bug UX (CTA recouvert par la carte Leaflet) via `page.evaluate().click()` au lieu de le détecter.

## Ordre de correction recommandé
1. **B3 + B4** (RLS insert + XSS admin) — faille exploitable à distance, quelques heures.
2. **B5 + E1** (perte offline + user_id) — cœur fonctionnel, factoriser la soumission dans `src/lib/tunnel.ts`.
3. **B1 + B2** (Kkiapay sandbox + vérif serveur) — bloquant pour tout encaissement.
4. **B6 + E6/E7/E8** (sync natif + signing + Firebase + commit) — avant toute distribution mobile.
5. **E2 + E4 + E5** (PWA installable + poids) — UX/perf contexte Bénin.
6. Moyens + accessibilité + tests (extraire `pricing.ts`, couvrir Kkiapay et la soumission).

Note transverse : ~60-70 % des ~4 000 lignes des 5 tunnels est du copier-coller. Extraire `escapeHtml`, `submitReservation(...)`, `goToWhatsapp(...)`, `validPhone/validEmail` et un composant « page adresse » paramétrable éliminerait ~1 500 lignes et plusieurs des divergences boguées ci-dessus d'un seul coup.
